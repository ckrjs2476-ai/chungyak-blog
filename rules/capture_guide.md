# 캡처 넣기: 실제로 연 화면으로 '직접 확인한' 흔적 남기기 (2026-10-25)

목적: '가치가 별로 없는 콘텐츠' 거절을 줄이기 위해, 글에 실제 원자료 화면을 확인한 흔적(캡처 + 사람 말투 캡션)을 넣는다.
캡처는 GitHub Actions(capture.yml)가 실제로 사이트를 열어 찍는다. 그래서 '확인 중', '열어 봤어요'는 사실이다.

## 1. 하면 안 되는 것 (지어낸 경험 금지)
- 캡처에 없는 행동을 쓰지 않는다: 모델하우스 방문, 실제 청약 신청·당첨, 투자해서 번 돈, 전화 문의, 현장 답사.
- 캡처에 보이지 않는 내용을 캡션으로 단정하지 않는다. 캡션 숫자는 화면에 보이고 데이터에도 있는 것만(가능하면 숫자 없이).
- 로그인·개인정보가 필요한 화면은 찍지 않는다. 개인 이름·전화번호가 크게 보이면 다른 부분을 자른다.

## 2. 캡처 방법
1. captures/queue.json에 항목을 넣고 commit·push → capture 워크플로가 captures/<name>.webp(가로 760px)와 captures/log.json을 남긴다(1~2분, gh로 완료 확인 후 git pull).
   - 전체 화면: {"name": "...", "url": "..."}
   - 부분: {"name": "...", "url": "...", "crop": {"from": "시작 글자", "to": "끝 글자"}} 또는 {"crop": {"from": "..."}, "height": 700}
   - 이름 규칙: <블로그 약자>-<대상>-<무엇>, 예: cy-2026000508-special, ipo-<corp_code>-dart
2. log.json에서 ok:true와 크기만 확인한다. 이미지는 처음 쓰는 레시피일 때만 열어 본다(토큰 절약).
3. 원고에 한 줄로 넣는다: `![캡션](captures/<name>.webp)` (빈 줄로 앞뒤 분리). publish.py가 글 안 그림(data URI)과 캡션으로 바꾼다.

## 4. 캡션 쓰는 법 (사람이 쓴 것처럼)
- 한 줄, 블로그 말투(청약·공모주·관리비 해요체, 전세 합니다체)로 가볍게. 사진을 정의하지 말고 보고 있는 상황을 말한다.
  - 좋음: "이번 주 청약 뭐 있나 청약홈 목록부터 확인 중~", "99도 같은 화면으로 확인. 84㎡ 줄은 신혼부부 칸이 제일 두툼해요", "증권신고서 열자마자 핵심투자위험 알림문부터 떠요"
  - 나쁨: "[그림 1] 청약홈 특별공급 공급대상 표", "아래는 ~에 대한 캡처입니다"
- 캡처 바로 앞 본문에 그 화면을 어디서 어떻게 여는지 한 문장(독자가 따라 할 수 있게). 같은 캡션 문구를 다른 글에서 되풀이하지 않는다.
- 글 하나에 1~2장. 캡처가 글의 중심 비교(표·순위)를 대신하지 않는다.

## 5. 매일 점검에서
- 하루 1편(블로그 상관없이, 네 블로그 모두(블로그를 돌아가며)). 우선순위: value 점수 낮은 글 > 검토자 '보완' 글 > 최근 글.
- 넣은 뒤 검수 통과 → commit·push(rerender-on-edit가 반영). 사본을 사용자 폴더에 넣는 일은 사용자가 대화에서 요청할 때만.

## 6. 경험 요소 넣기 (2026-10-28 사용자 요청: "내가 한 것처럼")
글은 블로그 운영자가 직접 찾아보고 정리한 기록처럼 쓴다. 단, **실제로 한 일만** 1인칭으로 쓴다. 이 블로그가 실제로 하는 일은 아래 7가지다.
| 요소 | 실제 근거 | 문장 예 |
| --- | --- | --- |
| 1. 원자료 직접 조회 | capture 워크플로가 실제로 연 화면(캡처 첨부) | "청약홈에서 공고를 열어 보니 특공 표가 먼저 눈에 들어왔어요" |
| 2. 매일 같은 기준으로 기록 | data/history (2026-10-18부터 매일) | "10월 18일부터 매일 같은 기준으로 적어 보니 서초구 숫자가 …" (값은 _changes.json 그대로) |
| 3. 공고→결과 이어 보기 | 같은 단지의 이전 글(링크) | "공고 때 정리해 둔 단지라 1순위 결과가 나오자마자 이어서 봤어요" |
| 4. 분석 과정 이야기 | 글의 비교 표 자체 | "구 평균만 볼 땐 몰랐는데 동별로 쪼개 보니 두 묶음으로 갈렸습니다" |
| 5. 신고서 버전 비교(공모주) | DART 첫 신고서와 정정 신고서 | "첫 신고서와 정정 신고서를 나란히 놓고 보니 청약일만 바뀌었어요" |
| 6. 독자 입장에서 보는 순서 | 의견(사건 아님) | "신혼부부 특공을 생각한다면 저는 이 칸부터 볼 것 같아요" |
| 7. 같은 화면 다시 확인 | 같은 레시피로 다른 날 캡처 | "일주일 뒤 같은 목록을 다시 열어 보니 …" (두 캡처가 다 있을 때만) |
- 글 하나에 1~2곳, 자연스러운 자리에만. 매 글 같은 문장으로 시작하지 않는다(틀 반복은 검수가 잡는다).
- 절대 쓰지 않는다(지어낸 경험): 모델하우스·현장 방문, 거주("제가 사는 동네"), 청약 신청·당첨, 투자·수익·손실, 관리사무소·분양사무소 전화/상담, 지인 사례, 내 고지서 실물, 밤새 했다 같은 과장. 이런 문장은 애드센스·구글의 '기만적 콘텐츠'로 블로그 전체를 위험하게 한다.

## 7. AI 티 금지 + 고친 흔적 금지 (2026-10-28, 검수가 막음)
- 검수(src/check.py style_errors)가 막는 표현: 셈이에요/셈입니다/인 셈, 라는 점에서, 포인트는, 것으로 보입니다/보여요, 눈에 띄는, 살펴보면, 알 수 있어요/습니다, 라고 할 수 있, 굵게(**) 강조한 문장, '~할 수 있어요.'로 끝나는 문장 3개 이상. 기존 BANNED 목록(주목할 점은, 결론적으로 등)도 그대로.
- 글을 고칠 때 고쳤다는 사실을 글에 남기지 않는다: "이 글을 처음 쓴/올린 …", "수정했어요", "업데이트", "(10월 22일 추가)" 같은 문장 금지. 바뀐 사실은 "10월 18일 집계에서는 …였고, 10월 24일 집계에서는 …"처럼 데이터 날짜로만 쓴다(검수가 막음).
